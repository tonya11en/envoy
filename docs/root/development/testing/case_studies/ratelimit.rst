Case Study: RateLimit Filter Integration Test
=============================================

This case study walks through the integration tests for the HTTP RateLimit filter,
demonstrating how to test complex gRPC-based interactions within Envoy's integration
framework.

The source code for this test can be found in
``test/extensions/filters/http/ratelimit/ratelimit_integration_test.cc``.

Narrative A: Day in the Life of a Request
-----------------------------------------

Tracing a single successful request through the RateLimit integration test reveals the
interplay between multiple upstreams and the filter's asynchronous gRPC logic.

1.  **Client Initiation**: The test client (``codec_client_``) sends an HTTP request to
    Envoy. In the ``Ok`` test case, this is a ``POST`` request to ``/test/long/url``.
2.  **Filter Interception**: The ``envoy.filters.http.ratelimit`` filter receives the
    request. It consults the route configuration to determine if any rate limit actions
    apply.
3.  **gRPC Request Generation**: The filter generates a ``ShouldRateLimit`` gRPC request
    containing descriptors (e.g., ``destination_cluster: cluster_0``) and sends it to the
    configured ``ratelimit_cluster``.
4.  **Fake Service Interaction**: The test's fake upstream, acting as the RateLimit
    service, receives the gRPC request. The test code uses ``waitForRatelimitRequest()``
    to capture and verify the content of this gRPC message.
5.  **Service Response**: The test explicitly instructs the fake service to respond using
    ``sendRateLimitResponse()``. For a success case, it sends an ``OK`` code.
6.  **Filter Resumption**: Upon receiving the ``OK`` response, the RateLimit filter
    allows the original HTTP request to continue its journey.
7.  **Upstream Delivery**: Envoy forwards the request to the backend upstream (in this
    test, an ``AutonomousUpstream``).
8.  **Final Response**: The backend upstream responds with a ``200 OK``, which is
    propagated back through Envoy to the test client.

Narrative B: Component-by-Component
-----------------------------------

The Test Client (Downstream)
^^^^^^^^^^^^^^^^^^^^^^^^^^^^
The client uses ``IntegrationCodecClient`` to initiate traffic. It is responsible for:
*   Establishing the connection to Envoy's listener.
*   Sending HTTP requests with specific headers to trigger rate limiting rules.
*   Waiting for and validating the final HTTP response (e.g., ``200 OK`` or ``429 Too Many Requests``).

Envoy (Filter Under Test)
^^^^^^^^^^^^^^^^^^^^^^^^^
Envoy is configured with:
*   A listener containing the RateLimit HTTP filter.
*   Route configuration that defines rate limit actions (e.g., based on the destination cluster).
*   A ``ratelimit_cluster`` pointing to the fake gRPC service.

The RateLimit Upstream (Fake gRPC)
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
This is a ``FakeUpstream`` configured for HTTP/2 to support gRPC. Unlike the backend,
it requires manual intervention in the test code:
*   **Connection Management**: The test must wait for Envoy to connect to it.
*   **Stream Handling**: The test must wait for the ``ShouldRateLimit`` stream and
    decode the protobuf request.
*   **Response Control**: The test manually encodes and sends the gRPC response to
    simulate various service behaviors (OK, Over Limit, Error).

The Backend Upstream (Target Service)
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
In many RateLimit tests, an ``AutonomousUpstream`` is used as the final destination.
Since the focus is on the RateLimit filter's logic, the backend simply provides a
valid response once the filter allows the request to pass.

Common Pitfalls
---------------

gRPC Upstream Setup
  When testing gRPC-based filters, ensure the cluster name in the filter config matches
  the cluster name added to the bootstrap, and that the cluster is configured to use
  HTTP/2 (via ``ConfigHelper::setHttp2``).

Expectation Ordering
  Because ``FakeUpstream`` is used, the test must follow the exact sequence of
  network events. Calling ``waitForNextUpstreamRequest()`` on the backend before
  the RateLimit gRPC exchange has finished will often lead to a timeout, as the
  filter is still blocking the request.

Descriptor Matching
  RateLimit tests often fail because the descriptors generated by the filter don't
  match the expectations in the fake service. Always use ``DebugString()`` or
  specific field checks to verify the ``RateLimitRequest`` message received by the
  fake upstream.

Troubleshooting
---------------

.. list-table::
   :widths: 20 40 40
   :header-rows: 1

   * - Symptom
     - Cause
     - Fix
   * - Test times out in ``waitForRatelimitRequest``
     - Envoy cannot connect to the fake gRPC upstream or the filter is not triggered.
     - Verify the ``ratelimit_cluster`` address matches the fake upstream's port and
       ensure the route configuration has ``rate_limits`` defined.
   * - Unexpected ``429 Too Many Requests``
     - The fake RateLimit service was programmed to return ``OVER_LIMIT``, or
       multiple requests were sent and the filter is behaving correctly but
       unexpectedly for the test.
     - Check the ``sendRateLimitResponse`` calls in the test and verify the
       logic for descriptor generation in the route config.
   * - gRPC metadata missing in response
     - The fake upstream sent a raw HTTP response instead of a proper gRPC stream.
     - Use gRPC-specific helpers like ``startGrpcStream()`` and ``sendGrpcMessage()``
       instead of raw ``encodeHeaders()``.
